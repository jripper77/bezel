D-2026-10-01-gif-sticker-search-5 (2026-10-01): The collection is core data behind a second driven port, `GifCollection`, shaped like `ArchiveStore`: load and save the index atomically (an unreadable index is an error naming it, never an empty collection), keep, read and discard bytes by SHA-256. Adapters: `DiskCollection` in bezel-media at `<data>/bezel/collection/` (`collection.json`, `files/<sha256>.gif`, `previews/<sha256>.gif`; the data folder the CLI and the studio both resolve) and `MemoryCollection` for tests. "Add to collection" (use case in `app::gifs`) takes the largest GIF rendition of at most 25 MiB (`REV_C_MAX_UPLOAD_BYTES`, so the file can also be sent to a screen as it is), downloads it with that limit, refuses bytes that are not a GIF, keeps one copy per content and records its name (the title, editable), kind (gif or sticker), size in pixels and bytes, time added, source (provider, id, page URL, kept so the design stays reversible) and the preview already fetched. GIF only: the renderer decodes GIF; WebP and MP4 renditions are backlog. The Media tab gets two subtabs, "This theme" (today's list) and "Collection": filter All / GIFs / Stickers, count and total size, and per item Add as image, Use as background, drag onto the canvas (an image element where it is dropped), Rename (inline) and Delete behind an in-app confirmation naming the user's themes and the open theme that hold the same bytes (they keep their own copy and go on working). Using an item copies its bytes into the theme's assets under its name through today's paths (`add_image_bytes` for an image, with no ffmpeg; an animated GIF background with its poster as now), so a sticker's transparency is the renderer's alpha compositing, with no new step, in vertical and horizontal themes alike (the element centered on the canvas).
