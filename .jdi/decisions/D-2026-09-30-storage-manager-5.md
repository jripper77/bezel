D-2026-09-30-storage-manager-5 (2026-09-30): The catalog and the local copies live in the user's data folder that the CLI and the studio both resolve, `<data>/bezel/storage/` (`$XDG_DATA_HOME` or `~/.local/share`, `%APPDATA%` on Windows: the CLI's `data_home`, Tauri's `data_dir`, as for `bezel/themes`): one `catalog.json` written atomically, copies stored by content (`files/<sha256>.<ext>`, the same bytes on internal and card kept once) and thumbnails (`thumbs/<sha256>.png`). A screen's catalog is keyed by its model id plus an optional name the user gives it (default: the model alone), since no screen can be told apart over USB (the 8.8" SoC has no iSerial; the MCU's `CT88INCH` is a model code); a fingerprint of the stored files is not used because it changes with every upload. Entries are keyed by medium, folder and name; a card entry also keeps the card's total capacity from GET_STORAGE_INFO, the only card trait the protocol shows, so a card of another capacity shows the other card's entries as "on another card", restorable. An entry records size, SHA-256, the source path on the PC, kind, duration and resolution when probed, the time sent and a state: `pending` (written before the upload starts), `stored` (after the size check), `missing` (absent from a listing; never dropped on its own) or `deleted` (deleted through Bezel). Every Bezel upload (put, the Storage view, the theme video, move, rename, restore) records the exact bytes sent (a converted video's output), and the boot media Bezel last set is recorded. Decided in auto mode (/jdi-discuss): the protocol shows no unique id, and content addressing keeps one copy per file.
