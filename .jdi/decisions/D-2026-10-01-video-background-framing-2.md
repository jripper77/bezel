D-2026-10-01-video-background-framing-2 (2026-10-01): A video background carries a framing: rotation (clockwise quarter turns 0..3 in the core, 0/90/180/270 in the JSON, or Auto), fit (cover = fill, the default; contain = fit, the uncovered area painted with an opaque pad color, black by default), zoom (1.0 to 4.0 on top of the fit's scale, default 1.0) and position (x and y in 0..1, default 0.5, with CSS object-position semantics: on an axis where the picture overflows it picks the visible part, where it is smaller it places the picture, so cover never shows a blank edge). In `.bezeltheme` (schema stays 1) it is an optional `framing` object inside the video background, e.g. `{"rotation":270,"fit":"contain","zoom":1.25,"position":{"x":0.5,"y":0.4},"padColor":"#000000ff"}`: omitted when everything is default, a missing key takes its default, out-of-range numbers are clamped and a rotation other than 0/90/180/270 is a DtoError, so older themes load unchanged and older builds ignore it. Auto (the key absent) is resolved wherever the video is used, from its probed size (MP4 header parsed in Rust, no ffmpeg needed): a video of exactly the panel's native size (480x1920 on the 8.8") in a theme whose canvas is an odd number of quarter turns from the panel is taken as already turned for the panel (the vendor keeps every theme video panel-native in `video\4801920\`) and gets the turns that cancel the theme-to-panel turns (Dragon Ball, landscape on the 8.8": 270, so 0 turns in total); any other size, an unknown size or a half-turned theme gets 0. The TURZX importer and the studio's "Add video" write no framing (the vendor zeroes its own TransFormInfo on load), so imported themes and the themes already in the library work without edits. Decided in auto mode (/jdi-issue).
